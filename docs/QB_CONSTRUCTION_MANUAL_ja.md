# PMAFでQuestionBankを作成する

版：0.2／更新日：2026-09-21

[English](QB_CONSTRUCTION_MANUAL_en.md) · [設定・ファイル・実装の詳細](QB_REFERENCE_ja.md)

このガイドでは、実験条件を設定し、経済統計の公表予定から問いを選び、資料と規約を付けてQuestionBank（QB）を作成する手順を説明します。完成したQBには、問い、予測者へ渡す資料、結果の判定規則、構築の記録が含まれます。

地域、統計機関、期間、問い数は実験目的に合わせて指定します。**「例：Eurostat版」には、公開済みの構築例で用いた値やコードを掲載しています。** これらの値はPMAF共通の指定ではありません。

**新しいQBを作る順序：** QBの構築・内容検査 → 保存した入力から再構築して一致を確認 → 正式な凍結 → 予測実験の開始。再構築による確認は、構築直後、実験開始前に行います。

| 行いたいこと | 読む箇所 |
| --- | --- |
| 新しいQBを作る | [1. 準備する](#prepare)から順に進む |
| 保存済みの入力からQBを作り直す | [7. 再構築して一致を確認する](#regenerate) |
| 設定項目やファイルの意味を調べる | [設定・ファイル・実装の詳細](QB_REFERENCE_ja.md) |
| エラーや不明な条件に対応する | [9. 問題が発生した場合](#troubleshoot) |

<a id="prepare"></a>
## 1. 作成に必要なものを準備する

**目的：** 作成するQBの用途と、作業に使う資料・実装を確認します。

1. 評価したい能力と対象を決めます。例として、経済統計を予測するAIシステムや、人間の予測者を対象にできます。
2. 公表日程、統計値、統計の定義を確認できる情報源を用意します。利用する評価プロトコルとデータスキーマの版も記録します。
3. 作業用フォルダーと、元資料を保存する場所を用意します。既存の凍結版がある場合は別の場所に保存します。
4. 収集・審査・選定を誰がどの方法で行うかを決めます。人間による収集、AI・プログラムによる処理、経済統計機関や民間企業が一般公開しているデータベースの検索、またはこれらの組合せを使えます。担当者・実装の版と判断の根拠を残します。

**完了の確認：** 評価目的、利用する規約・資料、担当、保存先が決まっています。

**例：Eurostat版**

公開コードは、特定のEurostat統計を使ってQBを構築・検証・再生成する実装です。他の地域・機関に適用する場合は、取得処理や生成文章などの改修が必要です。[改修箇所の一覧](QB_REFERENCE_ja.md#implementation)を確認してください。予測の配布、回答の受付、実際の結果取得・採点を自動実行する機能は含まれていません。

<a id="configure"></a>
## 2. 実験条件を設定する

**目的：** 収集する対象と、問いを採用する条件を先に決めます。

1. 設定ファイルまたは設定表に、評価対象、地域、統計分野、機関、実験期間、公表予定の対象期間を記入します。
2. 二値確率予測・点予測のどちらを使うか、問い数、提示から公表までの時間、回答時間、利用できる資料・情報源を指定します。
3. 適格性の基準、抽出方法、候補不足時の扱い、結果の公表版、採点方法、例外処理を決めます。詳細は[設定項目の一覧](QB_REFERENCE_ja.md#configuration)を参照してください。
4. 設定にIDと版を付け、収集前に収集条件を確定します。審査・選定の規則も、その処理を始める前に確定します。後で変更する場合は理由を残し、影響する処理をやり直します。

**完了の確認：** 必要な項目に具体値または決定規則があります。各選択が評価プロトコルに従い、設定の形式を検査するスキーマがある場合はその検査を通過しています。

**例：Eurostat版**

公表予定は2026年10〜12月、対象地域はEU27_2020・EA21、対象は6データセット、問い数は30、提示から公表まで336時間、回答時間は2時間、公表後の処理時間は24時間としました。設定は `banks/binary/global/config.json` にあります。入力はJSONです。YAMLの直接読込みと、設定全体を検証する完全なスキーマは現行コードに実装されていません。

<a id="collect"></a>
## 3. 公表予定と統計データを収集する

**準備するもの：** 確定した収集条件、経済統計機関や民間企業が一般公開しているデータベース・発表カレンダー、統計の定義資料、保存先。

経済統計機関や民間企業が一般公開しているデータベース・発表カレンダーには、次の例があります。

| 情報源 | 取得・確認できる情報の例 |
| --- | --- |
| [Eurostatのデータベース](https://ec.europa.eu/eurostat/web/main/data/database) | EU関連の統計値、系列の定義、メタデータ。公表予定は別途公式Release calendarで確認します。 |
| [世界銀行のOpen Data](https://data.worldbank.org/) | 各国の経済・開発指標と過去値。予測対象に採用する場合は、その統計の公表予定も確認します。 |
| [Trading Economicsの経済カレンダー](https://tradingeconomics.com/calendar) | 民間企業が公開する各国の経済指標の公表予定。採用する発表は元の公表機関の資料と照合します。 |

統計値を取得できることと、公表予定を取得できることは別に確認します。Webページの一般公開は、APIの無料利用やデータの自由な再配布を意味しません。利用するサービスの取得・保存・再配布条件を確認してください。

1. 指定した機関・地域・期間に従い、公表予定を取得します。問い合わせ条件、取得日時、取得した原応答を保存します。
2. 発表ごとに、統計系列、地域、参照期間、単位、調整区分、対象の公表版を特定します。一つの発表に複数の対象が含まれる場合は、対象ごとに分けます。
3. 同じ発表対象の重複を除き、採用する記録と理由を残します。日程変更は同じ対象の履歴として保存します。
4. 必要な過去値と定義資料を取得します。加工前の内容と、URL・クエリ・取得日時・応答状態・サイズ・SHA-256を対応付けて保存します。

**完了の確認：** 発表候補集合Uの各対象を元資料へたどれます。収集範囲、範囲外の記録、取得失敗、確認できなかった範囲を記録しています。対象地域のすべての統計を収集したとみなすには、別途その範囲を裏付ける根拠が必要です。

**例：Eurostat版**

[公式Release calendar](https://ec.europa.eu/eurostat/news/euro-indicators/release-calendar)から保存した55公表パッケージのうち、設定範囲内の18件を2地域に展開し、36発表対象を得ました。37件は範囲外です。数値には統計APIを使いました。`une_rt_m` のようなデータセット名に加え、年齢、性別、単位、地域などの次元も指定しています。[取得応答とJSON-statの扱い](QB_REFERENCE_ja.md#acquisition)に詳細があります。

<a id="screen"></a>
## 4. 問いの適格性を審査する

**準備するもの：** 発表候補集合U、問いのテンプレート、適格性の基準、根拠資料。

1. 各発表対象に事前に定めた有限のテンプレートを適用し、問い候補集合Pを作ります。
2. 次の項目を問いごとに確認します。判断は `PASS`、`FAIL`、`UNVERIFIED`（未確認）で記録します。

| 確認すること | 採用に必要な状態 |
| --- | --- |
| 対象範囲 | 指定した機関・地域・統計分野に含まれる |
| 問いの意味 | 系列、単位、参照期間、公表版、比較条件または点予測の目的量が明確 |
| 時間 | 提示・提出締切・公表予定・結果取得の予定が実験条件に収まる |
| 未公表性 | 予測対象の値が提供資料に含まれず、予測時点で未公表であることを確認する手順がある |
| 提供資料 | 必須の過去値、比較値、定義資料を用意できる |
| 結果の判定 | 指定した公表版から対象値を取り出す場所・方法が確認できる |
| IDと参照 | 問いIDが一意で、元発表と資料に対応している |
| 点予測の条件 | 目的量と損失関数が対応し、正規化する場合は尺度が正かつ有限 |

3. 各判定に基準の版、必須かどうか、出典、根拠、担当者またはコード版、確認日時を付けます。
4. すべての必須条件が `PASS` の問いを適格集合Cに含めます。資料作成後に確認する項目は、凍結前に再検査します。

**完了の確認：** 採否と理由を問いごとに説明できます。未確認の必須条件を残した問いは採用を保留しています。未公表性は、後の予測実行時にも確認します。

**例：Eurostat版**

構築時には36問が実装済みの検査を通過しました。ただし、現行コードの判定は主に二値で、未確認状態の三値管理は全面実装されていません。`resolution_defined` は取得先の説明が空でないことを検査します。必要な初回値を実際に取り出せることは、同種の既公表資料で別途検証します。公表時刻にも暫定値があるため、実際の実験前に確認が必要です。[時間と検査の制約](QB_REFERENCE_ja.md#implementation)を参照してください。

<a id="select"></a>
## 5. 問いを選定する

**準備するもの：** 適格集合C、必要な問い数、事前に決めた選定・不足・補充の規則。

1. 適格な問いのID一覧を保存します。これを選定の対象とします。
2. 全件採用、無作為抽出、層化抽出、意図的選定など、設定した方法を適用します。意図的に選ぶ場合は、測定する能力との対応と採否の理由を記録します。
3. 無作為抽出では、候補の固定順序、抽出単位、乱数生成器と実装の版、乱数種、抽出順、採用IDを保存します。
4. 候補が不足した場合や資料の準備に失敗した場合は、事前の規則に従い、件数の変更・補充・停止を記録します。

**完了の確認：** 採用集合Qと選定記録が対応しています。同じ対象の重複や、結果を見た後の差し替えがありません。

**例：Eurostat版**

36問から30問を非復元抽出しました。乱数種は20260912、候補はID順です。不足時は適格な全件を採用する設定でした。点予測版には同じ30対象を引き継ぎました。二つの版の計60口座は、30対象を二つの形式で表したものです。[抽出コードの例](QB_REFERENCE_ja.md#sampling)を参照してください。

<a id="assemble"></a>
## 6. 問いに資料と規約を付与する

**目的：** 各問いについて、予測者へ渡す内容と評価に使う条件をまとめます。

1. 問い本文に、対象系列、参照期間、予測する値または事象、提出形式を記入します。
2. 必須の過去データ、比較値、統計の定義、関連資料を収集・整備します。元資料、提供用に加工した資料、加工方法、版を対応付けます。
3. 提示時刻、回答時間、閲覧可能範囲、結果の判定基準、採点条件を付けます。共通規約と個別規約の矛盾がないか確認します。
4. 一つの問いと付随資料を一つの問い口座として格納します。口座をQBへまとめ、共通規約、索引、構築記録を付けます。
5. 予測者へ配布する範囲を明示します。将来の回答・結果・得点は未取得として扱い、構築時に作りません。

**完了の確認：** 各口座から必要な資料と規約を参照でき、問い本文と設定値が一致しています。共通規約は口座の外側、QBの内側にあります。

**例：Eurostat版**

各口座には `question.md`、`account.json`、`materials.md`、`local_rules.md`、`data/history.csv` を格納しました。履歴は構築時に取得した24か月分の版で、各月の初回値を集めたものではありません。ニュースや政策文書、他指標のデータ、長い定義文書の全文は添付していません。

予測時のネットワークアクセスは無効とし、予測市場とその確率の転載も禁止する設定です。これらは今回の例の情報条件です。

二値版は初回値が固定閾値を上回る確率を求め、等号はNOとします。点予測版は同じ初回値の条件付き平均を求めます。今回の総合指標は固定した履歴尺度によるNMSE、同じ系列・地域内ではMSEです。[ファイルと数値の扱い](QB_REFERENCE_ja.md#accounts)に詳細があります。

<a id="regenerate"></a>
## 7. 保存した入力からQBを再構築し、一致を確認する

**実施時期：** 新しいQBを構築した直後、正式な凍結と予測実験の開始前に行います。不備を早期に修正できるよう、実験終了を待たずに確認します。

**目的：** 保存した入力、同じ設定・コード・依存環境からQBを再構築（再生成）し、最初の構築結果と一致するか確認します。後日、情報源から最新データを取り直す操作は含めません。

**準備するもの：** 保存した元資料、構築時の設定・コード・依存環境、比較対象のQB、新しい出力先。

1. 最初に構築したQBを比較対象として保存し、その構築に用いた入力・設定・コード・実行環境を揃えます。新規構築時は、この比較対象が正式な凍結版である必要はありません。
2. 元QBと別の場所に構築結果を出力します。後日取得した最新データで元資料を置き換えないでください。
3. 比較するファイルの範囲を事前に定め、再構築したファイルの一覧とハッシュを最初の構築結果に照合します。毎回変わる実行日時や実行ログ、構築後に追加する凍結記録は、構築結果とは分けて記録し、比較対象の範囲を明記します。構造・参照・計算の検査も実行します。
4. 一致した範囲、差異、実行環境を記録します。不一致の原因を解消し、入力・設定・コードを修正した場合は、修正後のQBで再確認します。[問題が発生した場合](#troubleshoot)も参照してください。
5. 一致と内容検査を確認した後、[8. QuestionBankを検証・凍結する](#freeze)へ進みます。予測実験は正式な凍結後に開始します。

**完了の確認：** 指定した比較方法で構築結果が一致しています。バイト一致を求める場合は、改行・エンコーディング・JSONのキー順も含めて揃えます。同じ内容を再生成できることと、内容が正しいことはそれぞれ検査します。

### 例：公開済みEurostat版を再構築して検証する

以下は、既に公開・凍結されたQBを第三者が検証する例です。この検証は後日でも実行できます。新しいQBを作る場合は、上記の順序で構築直後・正式な凍結前に確認してください。

この例はWindowsのPowerShellで実行します。GitとPython 3.13.9を用意してください。初回の取得と環境準備には通信を使います。再生成処理はオフラインです。新規フォルダーを作成できる場所で始めます。

検査は `assert` を使うため、`python -O` を付けないでください。`-B` はキャッシュ作成を抑えます。環境、ログ、追加の出力は配布フォルダーの外へ保存してください。

1. 公開リポジトリを取得し、最初の公開版へ移動します。最新のコードを試す場合は、その版の手順と検証記録を確認してください。

   ```powershell
   git clone https://github.com/luntailangjianye33-stack/PMAF-Prospective-Macroeconomic-Announcement-Forecasting.git pmaf-example
   Set-Location pmaf-example
   git checkout 34bee8d0622d4735da7ed28342fb8481e547529b
   ```

2. `python --version` が `Python 3.13.9` であることを確認し、専用の環境を作ります。`../pmaf-qb-venv` は新しい保存先にしてください。

   ```powershell
   python --version
   python -m venv ../pmaf-qb-venv
   & ../pmaf-qb-venv/Scripts/python.exe -m pip install -r requirements.txt
   ```

3. 配布ファイルが保存された一覧と一致するか確認します。以降の操作はリポジトリのフォルダーで行います。

   ```powershell
   & ../pmaf-qb-venv/Scripts/python.exe -B scripts/verify_artifact.py .
   ```

   `PASS` が表示され、終了コードが0であれば次へ進みます。失敗した場合はその時点で止めます。

4. 保存した入力から二つのQBを再生成します。

   ```powershell
   & ../pmaf-qb-venv/Scripts/python.exe -B scripts/reproduce.py .
   ```

   結果の `status` が `PASS`、`binary_generated_files_identical` が207、`point_generated_files_identical` が211であることを確認します。生成物は一時フォルダーに作られ、終了時に削除されます。元のQBは変更されません。

5. 内容と凍結記録を確認します。各行を順に実行し、失敗したら次へ進まず原因を確認します。

   ```powershell
   & ../pmaf-qb-venv/Scripts/python.exe -B banks/binary/scripts/validate.py banks/binary
   & ../pmaf-qb-venv/Scripts/python.exe -B banks/point/scripts/validate_point.py --binary banks/binary --point banks/point
   & ../pmaf-qb-venv/Scripts/python.exe -B scripts/verify_freeze.py banks/binary
   & ../pmaf-qb-venv/Scripts/python.exe -B scripts/verify_freeze.py banks/point
   ```

   すべて `PASS` が期待されます。保存版の内容検査は二値版540項目・点予測版574項目、凍結照合は221ファイル・216ファイルです。再生成するファイル数とは対象が異なります。

[生成したファイルを手元に残す手順](QB_REFERENCE_ja.md#retain-output)と[実装の対応範囲](QB_REFERENCE_ja.md#implementation)も参照できます。

<a id="freeze"></a>
## 8. QuestionBankを検証・凍結する

**準備するもの：** 資料を整備したQB、適格性の記録、検査項目、凍結対象の一覧、および[再構築による一致の確認結果](#regenerate)。

再構築の確認後に入力・設定・コードや構築結果を変更した場合は、変更後のQBで確認をやり直してから凍結します。ここでのハッシュ照合は、保存したQBが凍結時の内容を保っているかを確認する操作です。前節の再構築では、構築処理を実行して同じ成果物を作れるか確認します。

1. 必須項目・型・値域、ID・ファイル参照、系列・単位・時間計算、資料の版と出典、各工程の件数を検査します。問い本文と規約も照合します。
2. 必須項目の不備を解消します。自動検査で確認したことと、人が内容を審査したことを別々に記録します。
3. 口座、資料、規約、設定、スキーマ、採否・抽出記録、元資料、構築コードなど、凍結する範囲を確定します。以後の変更は新版として管理します。
4. ファイルの内容が変化しない状態で、相対パス、バイト数、SHA-256の一覧を保存します。配布例ではこれを `manifest.json` としています。
5. 保存したmanifest自体のハッシュ、版、実施者、申告時刻、検査結果を凍結記録に保存します。manifest自身と凍結記録は、そのmanifestの計算対象から外します。
6. 保存後に一覧とハッシュを照合します。提示前に版が存在した証拠が必要な場合は、最初の提示前に独立した時刻の証拠も取得します。

**完了の確認：** 必須条件を満たしたQBを特定でき、ファイル一覧・内容・版を再検証できます。ローカルのハッシュと申告時刻だけでは、第三者に過去の存在時刻を証明できません。[凍結と公開時の扱い](QB_REFERENCE_ja.md#freeze-reference)を参照してください。

**例：Eurostat版**

各QBに `manifest.json` と `freeze.json`、配布パッケージに `ARTIFACT_MANIFEST.json` があります。口座は凍結対象に含め、マニュアルは外側の `docs/` に置いています。外部タイムスタンプは取得していません。将来の予測・結果・採点記録は、元口座を上書きせず、QBの版と問いIDを参照する別の記録として保存します。

<a id="troubleshoot"></a>
## 9. 問題が発生した場合

| 症状 | 確認すること・次の操作 |
| --- | --- |
| 公表時刻や対象系列を特定できない | 公式資料で確認します。必須条件が不明なら未確認として保留します |
| APIはHTTP 200だが数値がない | 次元と対象期間を確認します。欠測を0で補いません |
| 必要な問い数に届かない | 事前の不足時規則を適用し、実数を記録します。0件なら実験を開始しません |
| 必須資料や比較値が揃わない | 採用を保留し、補充・縮小・停止の規則を適用します |
| 点予測の尺度が0・非有限、履歴が不足 | 尺度の計算と元資料を確認します。選定済み標本との対応を記録して処理を止めます |
| スキーマ検査は通るが資料が見つからない | 資料パス、ファイルの存在、IDの対応を追加検査します |
| ファイルのハッシュが一致しない | 入力・コード・依存版、改行、JSONの順序、追加ファイルを比較します。原因を調べずmanifestを書き換えません |
| 後日のAPI値が異なる | 改定の有無を調べ、構築時の版を維持します。結果は指定した公表版から取得します |
| 出力先が既にある | 新しい保存先を指定します。凍結版を削除して使い回しません |

問い合わせや検証記録には、QB ID・版、問いID、操作、エラー、実行環境を含めます。認証情報は含めません。

設定項目、ファイル構成、出典、公開コードの制約は[設定・ファイル・実装の詳細](QB_REFERENCE_ja.md)にまとめています。
