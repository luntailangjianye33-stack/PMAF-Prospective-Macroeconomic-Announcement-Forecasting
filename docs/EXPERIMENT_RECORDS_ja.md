# PMAFの実行方法と記録の保存

[English](EXPERIMENT_RECORDS_en.md) · [QB作成ガイド](QB_CONSTRUCTION_MANUAL_ja.md) · [Eurostat構築例](../examples/eurostat_2026q4/README.md)

このガイドは、凍結したQBと、実験中・公表後に生じる記録の扱いを説明します。PMAFは手動、ソフトウェア、AI、またはそれらの組合せによる運用を許容します。Git等による版管理を推奨しますが、製品、保存形式、自動実行、自動コミット・プッシュ、更新頻度を一律に指定しません。

## 1. 共通の要件と実装手段を分ける

| 方法論として求めること | 選択できる手段の例 |
| --- | --- |
| 提示前にQBの内容と版を固定し、使用した版を特定する | 内容一覧・版番号・manifest・SHA-256・Gitコミット |
| 凍結版と後から増える記録を分離する | 別フォルダー、別のデータベース領域、別リポジトリ |
| 回答を問い・QB版・対象者・実行・受付時刻に対応付ける | 受付台帳、電子フォーム、API受付記録 |
| 情報条件の遵守を確認するために必要な証拠を残す | 配布記録、監督者の記録、許可したブラウザーやツールの履歴、取得資料 |
| 訂正前の内容、理由、訂正者と時刻を保持する | 旧版を保存した訂正台帳、追記による訂正、Git履歴 |
| 保存資料から構築・判定・採点を検証できるようにする | 元資料と判断の照合、コードの再実行、独立した再判定・再計算 |

各手段で同じ強さの証拠が得られるとは限りません。実験者は必要な記録、その取得方法、保存先、記録する時期、取得できなかった場合の扱いを実験前に定めます。必要な証拠が欠けた場合は未確認として扱い、記録が存在することだけで条件への適合を判断しません。

## 2. QBを固定し、実際に提示する版を確認する

QBを構築・検査した後、構築方法に応じた再検証を行います。プログラムによる構築では、保存した入力・設定・コード・依存環境から別の保存先へ再構築し、指定した範囲の一致を確認することを推奨します。実施時期は構築直後、正式な凍結と予測開始の前です。手作業の場合は、元資料、作成手順、設定、採否の記録から再検証できる状態を確認します。

内容・版を確定して凍結し、使用する版を実験記録へ記載します。manifestを使う場合は対象範囲とそのハッシュを保存し、実際の提示資料を対応する凍結資料と照合します。提示用に資料を変換する場合は、変換方法と提示物との対応も記録します。凍結したQBに訂正が必要なら、旧版を保持して新版を作ります。

コードの再実行による一致は構築処理の再現性、凍結時のハッシュとの照合は保存内容の対応を確認します。後日の最新データの再取得は、保存した入力からの再構築とは区別します。

## 3. 回答群と後続記録を別に保存する

以下は説明用の配置例です。実装済みのランナーや必須のディレクトリ仕様を表すものではありません。

```text
experiment/
├── questionbanks/qb_v1/      固定した問い・資料・規約・版の記録
├── runs/run_001/             提示、回答受付、根拠、取得・閲覧履歴、例外
└── evaluation/run_001/       公表資料、結果判定、得点、集計、訂正
```

凍結した口座の未記入の回答欄・結果欄を後から埋めません。後続記録からQBの識別子・版、問いID、実行ID、提出IDを参照します。manifestを採用した場合は、そのハッシュも対応付けます。同じリポジトリに保存しても、別の保存先を用いても構いません。

| 記録 | 保存する内容 |
| --- | --- |
| 実行の識別 | QB・問い・対象者またはシステム・実行の識別子と版、適用条件、提出先 |
| 提示・受領 | 提示資料の識別情報、実際の利用可能時刻・受領時刻、その測定位置と根拠 |
| 回答受付 | 原回答、確率または点予測値、提出ID、受付側の時刻、形式検査、採用する提出との対応 |
| 根拠・情報利用 | 規約で必要とした説明・証拠、取得元、取得時刻、資料の保存版または内容識別情報、必要な閲覧・操作履歴 |
| 例外・訂正 | 未提出、障害、規約違反の疑い、訂正前後の記録、理由、担当者、判断時刻 |
| 結果・採点 | 指定した公表版の資料、抽出した結果、判定者またはコード版、対象提出、採点規則・得点、期間末の状態 |

訂正は原記録を保持して追加します。実験終了後の再判定・再計算でも、元の結果と変更理由を残します。新しい回答や得点の追加によってリポジトリ全体のコミットIDが変わることは正常です。凍結したQBの固定範囲と、後続記録の各確定版をそれぞれ検証します。

## 4. 手動運用の例と、自動化する場合の案

右列は将来の実装を検討するための例です。Gitによる自動コミット・プッシュは、記録の保存や追跡に役立つ可能性がある将来の実装案です。本成果物では実装しておらず、導入効果も検証していません。

| 工程 | 手動運用の例 | ソフトウェア・AIを用いる運用の例 |
| --- | --- | --- |
| 提示 | 担当者が指定版の資料を渡し、配布記録を残す | 配布処理がQB版を照合し、提示内容と時刻を記録する |
| 回答受付 | 受付者が原回答と受領時刻を台帳に対応付ける | 受付サービスが原提出と受信時刻を保存する |
| 情報利用 | 提供資料と監督記録を保存する | 許可したツールから取得・操作履歴を受け取る |
| 保存 | 担当者が所定の区切りで保存・照合する | 自動保存し、必要に応じてコミット・送信する |

回答の受付と保存先への転送を区別します。転送障害時の保持・再送・欠落確認を事前に決め、転送の完了時刻を回答の受付時刻に置き換えません。

## 5. Gitを採用する場合の推奨事項

Gitは版の特定、差分の確認、過去の記録へのアクセスに用います。使用するQBの完全なコミットIDを実行記録に保存し、凍結版のファイルを変更せず、後続記録だけを追加します。コミット・送信の区切りは実験者が決めます。各回答時の自動プッシュは将来の案であり、必須ではありません。

履歴の上書き・削除を制限し、遠隔の保存先へ複製する運用を推奨します。実験中の回答を公開リポジトリへ送る必要はなく、他の対象者への漏洩を避けるため保存先のアクセス範囲を情報条件に合わせます。Gitはコミットしていない変更や実際の閲覧を自動記録しません。

Gitのコミット日時は利用者が設定できるため、提出期限への適合は受付記録から判断します。独立した時点の証拠を必要とする公開評価では、外部タイムスタンプ等を組み合わせます。ハッシュ、コミット、署名のみから、内容の正しさ、提出時刻、実験中ずっと変更がなかったことを推定しません。

## 6. 時間条件を満たさない場合の扱い

**実験前に決めること：** 評価プロトコルと実験設定に、提示・公表時刻のずれや実際の先行時間の許容範囲、結果判定・採点の期限、主評価への採否規則、比較に使う共通の問い集合の決め方を記載します。予測の収集前に確定し、予測値や得点を見て緩和しません。以下はPMAFとして推奨する運用方針です。

| 状況 | 主評価と記録の扱い |
| --- | --- |
| 公表のずれが事前の許容範囲内 | 前向き性・情報条件等の適格性と評価期限も満たせば主評価に含めます。予定・実際の時刻と差を保存します。 |
| 公表延期等で時間条件を外れる | 当初条件の主評価から除外し、問い、原提出、条件、理由を保持します。結果確定後の採点は補足評価に分けます。 |
| 評価期限までに結果が確定しない | 未解決として保存し、NO・誤答・仮の得点を代入しません。後日採点しても、期間末の状態と主評価を遡って変更しません。 |
| 早期公表により提出前に対象値が公開された | 影響する提出を、その値に対する前向き評価から除外します。公表前の提出も、実際の時間条件と比較集合の規則を確認します。 |
| 特定の予測者だけが提出期限を超えた | その提出を主評価から除外し、対象ごとの提出状況に反映します。問い全体を自動的に除外せず、比較集合の事前規則を適用します。 |

**処理する順序：** まず原資料・予定時刻・実測時刻と根拠を保存し、問いの状態と各対象の提出状態を分けます。確認できない事項は未確認として保留し、事前規則に基づく判定と理由、担当者、判定時刻を記録します。規則にない事象は影響部分を保留して扱いを記録し、予定外の分析として明示します。凍結QBを変更せず、これらは後続記録へ追記します。

**報告すること：** 得点と採点対象数に加え、当初の問い数、未解決数、除外数、理由別件数、対象ごとの提出状況と各分母を示します。一つの問いに複数の理由がある場合は重複を明示し、独立した問いとして足し合わせません。比較対象には共通集合を用いる規則を適用し、対象別の得点も示す場合は、それぞれの集合と件数を併記します。

採用・除外された問いの地域・統計分野等を比較し、偏りがないか確認します。主評価の解釈は採点できた問いと条件の範囲に限定します。後日解決した問いや異なる時間条件の問いを含む補足評価では、その集合、実際の時間条件、集計時点を明示します。除外が無偏りの評価を保証するとは扱いません。

これらは今後の実験で採用する規則を具体化するための説明です。公開済みEurostat例の凍結規約は変更しておらず、この例で例外処理や予測実験を実行・検証したという意味ではありません。別の規則を採用する場合は、予測開始前に新しい版を確定してください。

## 7. 現在のEurostat構築例

`examples/eurostat_2026q4/`には凍結済みQB、元資料、構築・検証コードを配置しています。予測実行、回答受付、閲覧履歴収集、結果取得・採点の自動運用、自動プッシュは実装していません。実際の実験を始める場合は、対象と日程の適格性を再確認し、実験記録の保存方法を別途用意してください。
